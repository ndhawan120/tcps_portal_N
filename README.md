# TCPS Professional Development Portal

A role-based internal professional development portal for TC Professional Services. The application supports employee ACCA/PER tracking, manager review workflows, organisation administration, reporting, announcements and profile management.

## Stack

- Next.js 14 / App Router
- React 18 + TypeScript
- Tailwind CSS
- Supabase Authentication, PostgreSQL and Row Level Security
- Vercel hosting

## Role structure

### Employee

- Dashboard — personal summary and next actions
- Exam / PER — the canonical learning and PER workspace
- Documents — PER evidence notes and supporting information
- Updates — announcements
- Profile — personal professional information

Employees only see their own development information. They do not see Team, People, Approvals, Reports or Admin.

### Manager

- Dashboard — personal summary and management shortcuts
- Exam / PER — development workspace
- Team — direct-report progress and action queue
- Approvals — PER submissions requiring manager action
- Reports — analysis and KPIs for assigned employees
- Updates
- Profile

Managers only receive team data through `profiles.manager_id`. They should not see other managers' employees.

### Admin

- Dashboard — organisation summary and configuration shortcuts
- Exam / PER — development workspace
- Team — **Workforce Overview**, focused on active employee visibility, team relationships and operational progress
- People — complete office directory: employees, managers and admins
- Approvals — organisation-wide approval workflow
- Reports — organisation-wide analytics and KPIs
- Admin — system administration
- Roles & Access — custom business role names and departments
- Updates
- Profile

## Tab responsibilities

The portal intentionally separates operational work from reporting:

- **Dashboard:** summary and entry point; do not duplicate full datasets here.
- **Team:** what needs attention and who needs action. Managers see direct reports; admins see active employees.
- **People:** source of truth for office people records and people actions.
- **Approvals:** source of truth for PER approval workflow.
- **Reports:** analysis, rates, distributions and KPI interpretation; not another employee directory.
- **Documents:** currently PER evidence notes. It is not yet a general-purpose file-management system.
- **Admin / Roles & Access:** configuration, roles and departments.

## Canonical routes

Use these URLs for all new internal links:

| Area | Canonical route | Access |
|---|---|---|
| Login | `/login` | Public |
| Dashboard | `/dashboard` | Authenticated |
| Exam / PER | `/exams` | Authenticated |
| Documents | `/documents` | Employee |
| Updates | `/announcements` | Authenticated |
| Profile | `/profile` | Authenticated |
| Team / Workforce | `/team` | Manager / Admin |
| Approvals | `/approvals` | Manager / Admin |
| Reports | `/reports` | Manager / Admin |
| People | `/employees` | Manager / Admin, with role-scoped data |
| Admin | `/admin` | Admin |
| Roles & Access | `/admin/roles` | Admin |
| Branding | `/admin/branding` | Admin |

Legacy routes may remain only for backward-compatible redirects. They must not be generated by internal navigation or `Link` components.

Notably, `/manager/*`, `/employee/*` and `/per-objectives` are legacy compatibility routes. The application should always generate `/team`, `/employees/...` and `/exams` internally.

## Internal linking principles

Every major summary should lead to its source or next action:

- Employee: Dashboard → Exam / PER → Documents & PER Evidence → back to Exam / PER.
- Manager: Dashboard → Team → Employee profile → Approvals or Reports as appropriate.
- Admin: Dashboard → Workforce / Team for progress, People for records, Approvals for workflow and Reports for analysis.
- Reports → Team, People or Approvals when the user needs to act on the information.
- Employee names should link to canonical `/employees/{profile_slug}` URLs, never UUID URLs.

## Data rules

- **22 PER objectives** remain the source-of-truth objective total.
- **13 ACCA exam papers** remain the tracked exam total.
- Manager reporting is scoped through `profiles.manager_id`.
- Admin reporting is organisation-wide where appropriate.
- Approval and people actions require authenticated server-side authorization.
- Do not introduce duplicate hard-coded totals in individual pages.

## Departments

Departments are managed through the Admin → Roles & Access area and should be selected consistently in user-facing forms. Profile and Add User forms use active managed departments instead of independent free-text lists.

When a department is renamed in administration, assigned profiles are migrated to the new department name. Department deletion is blocked while profiles remain assigned.

## Permissions

The security model uses multiple layers:

1. Navigation hides areas that are not relevant to a role.
2. Middleware protects role-sensitive routes.
3. Server pages verify the authenticated profile and active status.
4. Sensitive API handlers perform their own authorization.
5. Supabase RLS remains the database-level boundary.

Recommended access matrix:

| Area | Employee | Manager | Admin |
|---|---:|---:|---:|
| Dashboard | Own | Own/team summary | Organisation summary |
| Exam / PER | Own | Development context | Development context |
| Documents | Own | — | — |
| Team | — | Direct reports | Active workforce |
| People | — | Scoped people access | Full office directory |
| Approvals | — | Assigned employees | Organisation |
| Reports | — | Assigned employees | Organisation |
| Admin | — | — | Full |
| Roles & Access | — | — | Full |
| Updates | Read | Read | Manage where configured |
| Profile | Own | Own | Own |

## Documents status

The current Documents area displays PER evidence notes stored with objectives. It does not yet represent full uploaded-file management. A future file-management implementation should add Supabase Storage, document metadata, access rules, upload/delete behavior and retention rules deliberately rather than treating evidence notes as uploaded files.

## Development

```bash
npm install
cp .env.example .env.local
npm run dev
```

Set the required Supabase environment variables in `.env.local` and never commit secrets.

Before release:

```bash
npm run check
```

`npm run check` should pass linting, TypeScript validation and the production build before a production merge.

## Deployment

Production is hosted on Vercel and connected to this repository.

Recommended flow:

1. Create a backup branch before structural changes.
2. Work on a feature branch.
3. Run `npm run check`.
4. Review the Vercel preview.
5. Verify employee, manager and admin journeys.
6. Merge to `main` only when the preview is healthy.
7. Confirm production after deployment.

Production URL: `https://tcps-portal-n.vercel.app`

## Troubleshooting

### Vercel module-not-found errors

Check the import path and filename casing. Vercel builds on Linux, so imports must match filenames exactly.

### Unexpected role access

Check `components/Nav.tsx`, `middleware.ts`, the affected page and its API handler. Navigation visibility is never an authorization boundary by itself.

### Old URLs appearing internally

Search the repository for the legacy path and replace internal `Link` targets with the canonical route. Keep legacy middleware redirects only for external/bookmarked URLs.

### Material Symbols appear as text

Confirm the Material Symbols font import and `.material-symbols-outlined` styling remain present before changing navigation markup.
